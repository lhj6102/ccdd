# CCDD v2.0.0

CCDD를 Artifact·Critic·관계의 정의 전용 SDK로 분리하고, 프로젝트 검증과 실행 이력을 새 `@lhj6102/ccdd-project` 패키지로 옮깁니다. CLI 설치 패키지가 바뀌므로 세 패키지를 함께 2.0.0으로 배포합니다.

## 주요 변경

- **요청 시 계산하는 검증:** `status`와 `plan`이 DAG의 의존성을 재귀적으로 확인합니다. Artifact별 staleState를 저장하거나 변경을 하위 노드에 전파하지 않습니다. memoization은 한 조회 안에서만 사용합니다.
- **입력에 근거한 실제 판정 재사용:** Critic 조건, target과 직접 deps의 hash가 같고 선행 검증이 충족되면 기존 실제 PASS를 참조합니다. Why가 바뀌어 Spec을 재검토해도 Spec 내용이 같다면 Tests·Implementation의 검토는 재사용할 수 있습니다. 동일 입력에 대한 나중의 실제 RED는 과거 PASS보다 우선합니다.
- **Artifact stale 전략:** 기본 파일 hash, 명시적인 입력 경로 목록, 요청마다 검토하는 `always`를 지원합니다. 경로 목록은 해당 Artifact의 의미에 영향을 주는 입력을 모두 포함해야 합니다.
- **개별·재귀 검증:** `verify B`는 바로 실행 가능한 B Critic을 의뢰하고 막힌 항목은 미완료로 보고합니다. `verify B --recursive`는 필요한 선행 검증을 포함하고 준비된 실제 요청만 발급합니다. `--force`는 선택한 Critic을 다시 검토하며 선행 조건은 유지합니다.
- **분리된 저장과 모니터:** 실제 판정과 당시 hash, 실행·티켓 이력은 repo 밖 Project 저장소에 남깁니다. 모니터의 현재 입력 조회는 명시적인 버튼으로 수행합니다. 자동 GET은 설정 평가·도구 실행·리뷰 상태 변경을 하지 않습니다.

## 설치

Node.js 24 이상에서 Release의 core·Project·기본 도구 tarball을 내려받고 `SHA256SUMS`를 확인한 뒤 함께 설치합니다.

```sh
npm install --ignore-scripts \
  ./vendor/ccdd/lhj6102-ccdd-2.0.0.tgz \
  ./vendor/ccdd/lhj6102-ccdd-project-2.0.0.tgz \
  ./vendor/ccdd/lhj6102-ccdd-default-tools-2.0.0.tgz
npx ccdd-project config check
npx ccdd-project plan implementation --recursive
npx ccdd-project verify implementation --recursive --wait
npx ccdd-project status implementation
```

사용자 도구만 사용하는 경우 core와 Project만 설치합니다. 정의만 사용하는 경우 core만 필요합니다. npm registry에는 게시하지 않습니다.

[설치 안내](https://github.com/lhj6102/ccdd/blob/v2.0.0/README.md#시작하기) · [전체 명령과 저장 계약](https://github.com/lhj6102/ccdd/blob/v2.0.0/docs/project-validation.md)

## v1에서 이전

1. `@lhj6102/ccdd-project`를 추가하고 core·기본 도구의 버전을 함께 올립니다. `defineConfig`·`defineTool`의 import 경로와 기존 Artifact·Critic 설정은 유지합니다. stale 설정은 선택 사항입니다.
2. 새 검증 흐름에는 `ccdd-project verify`를 사용합니다. 기존 `ccdd` CLI는 Project 패키지에서 제공하며, `ccdd run`의 독립 실행 계약은 유지합니다.
3. 상태 저장은 기본 `~/.local/state/ccdd/<repo 경로 hash>/broker.sqlite`를 사용합니다. `--state-dir` 또는 `CCDD_STATE_HOME`으로 바꿀 수 있으며, 검토 대상 repo 밖이어야 합니다. 기존 실행·snapshot·Human 대기는 유지합니다. hash 근거가 없는 과거 리뷰는 조회할 수 있지만 새 검증의 PASS 근거로 재사용하지 않습니다.
4. 모니터는 새 CLI로 다시 시작하고, 완료된 미완료 실행의 후속 검증은 새 `verify`로 요청합니다. `verify --wait`는 0=범위 충족, 1=RED, 2=ERROR, 3=대기 시간 초과, 4=미완료입니다.

## 검증 범위

Release 절차는 지정한 커밋의 격리된 clone에서 빌드·전체 테스트와 세 tarball의 production 설치를 검증합니다. 기본 도구 구성과 사용자 도구 구성 모두 실제 도구·Runtime·분리된 worker 실행 및 티켓 없는 PASS 재사용을 검사합니다. 정확한 소스 커밋·환경·테스트 결과는 첨부된 `verification.json`에 기록합니다.

외부 Provider 평가와 사용자 데스크톱 연결은 설치 환경에서 `ccdd-project doctor` 및 선택한 도구의 `tools check --execute`로 확인합니다. 대규모 전체 workspace snapshot의 성능 개선은 이번 릴리스 범위에 포함하지 않습니다.
