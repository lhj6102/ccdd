# CCDD 7.1.0 — Cached dispatch and publication state

CCDD 7.1 fixes large cached submissions that admitted requests but never started
an executor ([#104](https://github.com/lhj6102/ccdd/issues/104),
[#105](https://github.com/lhj6102/ccdd/pull/105)). It adds an explicit
`publication` state and narrows the documented integrity contract for cache-owned
executions. The explicit identity remains the whole 7.x reuse key.

## Large cached submissions

A cache-owned execution reads the supplied workspace in place without creating
its own recursive watcher, metadata/content walks or adaptive metadata polls.
The submitting Run keeps its single workspace observer for its receipts and for
requests without an identity. `workspaceAdapter` is no longer passed to owner
Brokers just to reopen that workspace.

Measurements from #105, not a promise for every filesystem or workload:

| Synthetic: 1,000 identities, 971 files / 29 MiB, controlled executor, Provider capacity 4 | 7.0.0 | #105 measurement |
| --- | --- | --- |
| First executor start | None in 120 s | 2.0 s |
| Completed | 0 | 1,000 / 1,000 in 35 s |
| Workspace observers | 1,001 | 1 |
| Workspace root walks | 2,004 | 3 |
| Process bytes read | 11.9 GiB in 120 s, still rising | 0.64 GiB total |
| Peak RSS | 4.2 GB | 0.7 GB |

A private lostbuilds-rs check used all 845 evaluable Critics with a schema-valid
stub executor, no model calls, and private configuration and state:

| Private check | 7.0.0 | #105 measurement |
| --- | --- | --- |
| Admitted / identity preparation | 845 / 19 s | 845 / 19 s |
| First executor start after `run` | None in 180 s | 9.8 s |
| Completed | 0 | 845 / 845 in 103 s |
| Workspace observers / root walks | 846 / 1,694 | 1 / 7 |
| Completion identity re-runs | n/a | 845, one per owner |

| Event-loop delay p99 | 1,912 ms | 84 ms |

Of the private check's 42.1 GiB, 33.5 GiB came from existing per-attempt runtime-pin
hashing. The remaining startup cost depends strongly on SQLite backing storage:
the final revision's unchanged 1,000-owner scale acceptance measured 51.1 s to
first dispatch and 69.7 s to start all owners, with one observer, two root walks
and 81 MiB read. Per-owner initialization/fsync is a known residual cost, not a
regression introduced by #105; see [#106](https://github.com/lhj6102/ccdd/issues/106).

## Integrity of a cache-owned execution

After execution finishes, releases its machine resources and closes its own
store, the subscriber re-runs the owner identity function in the same workspace
under the machine identity lease. This check is the **last await before every
publication commit attempt**. A different value fails with `WORKSPACE_CHANGED`
and publishes nothing. Failed or timed-out identity checks also publish nothing.
There is no owner-store write after the final check.

**CCDD does not lock the workspace or copy its inputs. Callers must not edit
identity-covered input while an execution of that identity is in flight.** The
check detects covered changes completed before it runs, but cannot make
publication atomic against workspace edits:

- A change outside the identity no longer fails the shared execution.
- A covered edit restored before the check is not detected.
- Race (a), an edit racing the check itself after the identity function has read
  that input, is not detected. A regression test pins this documented limit.
- Race (b), a covered edit while execution cleanup releases resources, is checked
  afterward and rejected if the returned identity differs.

Human claim preparation re-runs the identity in its final validation. Human tool
calls perform claim checks only; Human result submission re-runs the identity
before recording the result, and publication checks again. Human waiting has no
owner workspace monitoring; owner death still fails the execution.

The submitting Run's observer is unchanged. A detected change fails its receipts
and detaches its subscriptions. A computation with no subscribers is aborted;
one still needed by another subscriber continues under the identity rule.
`--integrity metadata` applies to the submitting Run, not to cache owners.
See [the full contract](../identity-cache.md#integrity-of-a-cache-owned-execution).

## Publication is separate from the reviewer verdict

Cache-owned execution outputs expose `publication: { state, code?, message? }`:

- `accepted`: the cache publication transaction committed. GREEN and RED remain
  eligible evidence; RED still fails validation.
- `pending`: publication has not committed. The raw verdict is audit only.
- `rejected`: publication failed, with its failure code and message. The raw
  GREEN/RED remains unchanged as audit only, not accepted evidence.

Run/request views and summaries, lifecycle pages, result streams, request lists
and full/compact history expose the distinction. `queryProject` and `planProject`
exclude pending/rejected history from matching evidence, satisfaction and REUSE.
Pending/rejected audit does not produce a successful CLI stream/wait exit.
Ordinary receipts, unrelated uncached Runs and cache lookup semantics are
unchanged.

Readers resolve publication from the identity-cache job beside the execution
store, independently of the reader's `CCDD_STATE_HOME`. Terminal jobs remain
until execution audit storage is retired, including accepted oversized results
without a retained cache entry. Readonly inspection reports a dead RUNNING owner
as rejected / `COMPUTE_OWNER_EXITED`. Missing or unreadable publication metadata
fails closed as pending / `PUBLICATION_UNAVAILABLE`, never inferred acceptance.

## Monitor attention lane

Monitor listings, overview, detail and HTTP responses use the same publication
authority. Pending audit is projected as RUNNING with attention; rejected audit
as ERROR with attention and its failure reason. Neither enters the success lane.
`rawStatus` and the raw detail result preserve the reviewer verdict. Labels read
**Audit only · Publication pending/rejected**, not that the criteria passed.
Monitor GETs remain readonly and do not run identity scripts.

## Polling and remaining costs

The dispatch fix also removes per-owner I/O and repeated maintenance work:

- Receipt mirrors stat the owner store and WAL, opening the store only on change.
- Local subscribers wait for their task; after it is aborted, they read the
  authoritative stored outcome instead of waiting for its executor. Remote
  subscribers still poll.
- Cache maintenance uses one `json_each` statement per pass rather than two
  queries per owned computation.
- Every Broker in a process shares one machine-resource connection and one
  250 ms reclaim cadence per database, with synchronous transactions.
- Admission waiters wait behind an earlier local same-lane waiter only after
  that predecessor has been refused, preserving prompt admission for bursts
  that fit capacity.
- A cache-owned Run waits for its single request or cancellation instead of
  re-planning every 50 ms.

Remaining costs are tracked in [#106](https://github.com/lhj6102/ccdd/issues/106):
one Broker/SQLite store per identity, durable-storage schema/transaction fsync,
a CPU-only 100 ms ownership poll per owner, and repeated runtime-pin hashing per
attempt. Receipt mirrors can lag on filesystems with coarse timestamps until
another write; terminal publication remains authoritative. Ownership fencing,
cross-process joins, dead-owner recovery and the scale test's limits are unchanged.

## Compatibility

Four packages are aligned at 7.1.0. The umbrella pins all three modules to 7.1.0;
Project and default-tools keep the core peer range `>=7.0.0 <8`. Node.js 22 LTS
(22.19.0 or later) is required. Use matching versions, or install `@ccdd/ccdd`.
Stop earlier workers before upgrading; see [installation and upgrades](../releases.md#installing-and-upgrading)
and the [7.x migration](../migration-v7.md) when upgrading from before 7.0.
